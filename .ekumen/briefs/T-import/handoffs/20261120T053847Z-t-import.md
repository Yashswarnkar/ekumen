## OUTPUT

- `internal/legacyimport/`
  - `inputs.go` reads `registry.yaml`, `decisions/*.yaml` and contract front matter with go.yaml.in/yaml/v3 (D-yaml-library). It works over an `fs.FS`.
  - `briefs.go` reads new-layout briefs and splits the old single-file briefs (R1, R2, T0) into `briefs/<new id>/brief.md`, `amendments/` and `handoffs/`. The new `brief.md` gets the new id plus `aliases: [<old>]`. Each entry gets front matter with `source: briefs/R1-acp.md §B`. §B and §C entries carry only a date, so they are named `<date>T120000Z-<author>.md`, with the store's `-2` suffix when two land in the same second. It also parses handoff sections in both the `KEY:` and `## KEY` forms.
  - `build.go` builds the events. Event ids are ULIDs: the time is the event's `at`, and the entropy is a lifecycle rank byte followed by 9 bytes of SHA-256 over the content. So log order follows each record's lifecycle even when everything sits at 12:00:00Z on the same date.
  - `verify.go` runs `core.Reduce` and compares the result with every record: decision status, answer, answer_note, decided_by, decided_on, applied_on, superseded_by, title, tier; task status, approved, blocked_by, tier_grants, session, entry counts; contract status and version; every alias. It also lists skipped events, validates each record against C-decision-record §2, and runs `core.Conflicts` with the current brief and contract hashes.
  - `import.go` provides `Prepare`, which plans and writes nothing, and `Apply`. `Apply` refuses a plan with mismatches or conflicts. It writes the split brief files (O_EXCL), then appends events through `internal/store/files`, then removes the 3 old briefs.
- `cmd/ekumen-import` takes `--root` (default `.ekumen`), `--dry-run` and `--json`. Exit 1 means mismatches or conflicts.
- Tests:
  - fixtures copied from the real `.ekumen/` (`testdata/ekumen`)
  - golden events (`testdata/events.golden.jsonl`, refreshed with `-update`)
  - `TestDeterminism`: two plans on the same inputs and on two copies are byte-identical; a real run followed by a re-run writes nothing and leaves every file byte-identical; the log reads back through the store
  - a verification test that edits records and expects named mismatches, and checks that `Apply` refuses and nothing is written
  - a missing-mapping test
  - tests for the brief split and the handoff parser
  - command tests

**Choices worth knowing:**
- **orchestrator_note** (D-013, D-014) is kept as extra data, `legacy.orchestrator_note`, on the DecisionDecided event. A QuestionAsked/QuestionAnswered pair would have invented a question nobody asked and an answer nobody gave. An unanswered QuestionAsked would sit open in the lead's inbox forever. Extra data is allowed (C-event-log §2, §9) and loses nothing. The cost is that the core and projections don't show it yet (FOLLOW-UP).
- Anything with no contract field goes under one extra data key, `legacy`. That covers:
  - `raised_by_task` for the non-task values `vision`, `spine` and `public-repo`, which are imported as `task: null`
  - the old `applied: {amended, unblocked}` block, which names `spine §6` and contracts rather than tasks; the typed lists stay empty
  - D-license's (D-009) `answer_note` on DecisionDefaulted
  - contract `blocked_by` and `date_unknown`
- **Actors.** The lead is `lead:Yashswarnkar`, taken from `registry.yaml lead:`. A record's `decided_by: lead` is treated as that handle. Others are `orchestrator:orchestrator`, `session:<name>`, and `loop:loop` for the hand-done applies, the D-license default and the session attachments, so every event sits in its v3 lane.
- **Dates.**
  - Where only a date is known, the import uses 12:00:00Z on it.
  - An entry's file name gives its exact UTC time.
  - A task's approval time is its first "Approved by lead" amendment.
  - Records with no date are placed on the earliest date in the inputs (2026-11-19) with `legacy.date_unknown: true`. These are never-approved tasks and the two draft contracts.
- **Task status** needs observations (C-event-log §7.2). Verification turns the registry's `done`, `in_review` and `running` into PR merged, PR open and session running. `draft`, `approved`, `blocked` and `ready` must come from the events alone.
- **Re-runs.**
  - An event already in the log with the same bytes is skipped.
  - The same id with other bytes is an error.
  - A second creating or lifecycle event for a subject (for example, a registry row edited after an earlier real run) is reported as drift and not written.
  - After the real run, the import reads the split briefs instead of the removed files.

## FOLLOW-UPS

1. **internal/core `ValidateAlias` refuses `D-001`…`D-019`**, because they match the slug regex. C-event-log §1 itself names `D-012` as an alias. The import reports these as 19 validation failures caused by the core. The reducer resolves the aliases correctly.
2. **internal/core still has v1 lanes.** `DecisionRaised` is limited to session and integrator, so 14 lead- or orchestrator-raised records show as lane conflicts. The import lists them separately and does not fail on them. `TaskSessionAttached` is loop-only. `event.TaskDrafted` has no `session` field (v3), so the import writes `session` into TaskDrafted data and also writes a `TaskSessionAttached`, because only that one is read for own-task checks.
3. **internal/store/files** has no API to write `brief.md`, and none to write an entry with a given (historical) timestamp, because `WriteEntry` uses the clock. The import writes the split brief files directly, with O_EXCL and no overwrite.
4. **D-yaml-library** is decided but has no `applied_on`, so in events it still gates T-cli. T-cli shows `running` only because that status is observed. When the orchestrator applies it, it should be recorded before or at the switch.
5. **Approval dates.** The registry's `approved: 2026-11-20` for T-core and T-file-store is a local date. Their approval entries are 2026-11-19T20:07:12Z UTC, and the import uses the UTC time. Registry dates, `decided_on` and `frozen_on` look like local dates in general, which contradicts v3's "all dates UTC".
6. **T-cli's projections** should show `legacy.orchestrator_note`, `legacy.applied` and `legacy.raised_by_task`, or the regenerated `decisions/*.yaml` will drop them. YAML comments in records (D-014's `answer:` comment, D-018's `deadline:` comment) are not imported.
7. **Records breaking C-decision-record §2** were reported, not fixed:

   - tier 1 without a deadline: D-018
   - `raised_by` with key `true:` instead of `on:`: D-alias-field, D-blocker-semantics, D-entry-name-same-author-branches, D-lane-gaps, D-slug-length-scope, D-store-event-type-check, D-task-status-approved, D-urgency-formula. A YAML 1.1 writer turned `on` into a boolean. The import reads it as `on` and notes it.

## DEVIATIONS

- A `legacy` key inside event `data` for information with no contract field. Unknown data fields are allowed by C-event-log §2 and §9.
- Split entries add a `source:` line to their front matter.
- Contracts are imported at their current version (`ContractFrozen {version: 3}` for C-event-log), as amendment 20261120T052217Z says. Earlier versions are not replayed.

## FRICTION

- The registry `status` is half observed. Verifying `done`, `running` or `in_review` against events is circular, because those statuses are observations. Only the event-derived statuses can really be checked.
- Hand-written YAML had 3 dialects for one record: flow maps, block maps, and Python-dumped YAML with quoted dates and `true:` keys. A validator at write time would have caught the `true:` key.
- `applied` and `raised_by.task` predate any contract and mix prose ("C2 pending id migration", "spine §6") with ids.
- The brief says to use "12:00:00Z when only a date is known", but several events then share a millisecond, and the reducer is order-sensitive within a subject (approve before draft, apply before decide). The fix is to rank lifecycle steps inside the ULID entropy. The contract could say how imported or replayed events must be ordered.
- Main moved while I worked (C-adapter and C-http-api were drafted), so I restacked and re-ran the dry run. Expect this again at the switch: the import is meant to run on the latest main.
