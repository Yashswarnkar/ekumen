## OUTPUT

What changed, per finding:

1. update-after-close (#23). I picked the second option: the merged-PR branch is gone. The rule flags only a `TaskUpdated` that comes after the task's `TaskDeferred` in log order. A pending update on a done task is history, not a conflict; the inbox does not offer it, and `task approve` now refuses it ("<id> is done; its pending update can no longer be approved"), so inbox and approve agree. An update on an unapproved task that arrives by merge after its PR merged applies at once and is not a conflict (done has no place in the log). Tests: `TestTaskUpdatedAfterCloseIsReported`, `TestTaskUpdatedBeforeDeferIsNotReported`, `TestTaskUpdatedOnDoneTaskIsHistoryNotConflict` (approved and unapproved cases), CLI `TestTaskUpdatePendingOnDoneTask`.
2. graph `waiting_on` vs lead actions (#24). A decided or defaulted decision whose `apply` action is in the lead's inbox (a day after deciding) is `waiting_on: lead`, drawn as a gate labelled "apply is yours". The graph's lead nodes are exactly the inbox's decisions plus apply actions; `TestGraphWaitingOn` checks that before and 25 hours after a decision, and the map golden has both states.
3. Brief-moved predicate (#23). One function, `core.BriefFile(id, brief)` (leading `.ekumen/` dropped, path cleaned, empty brief = `briefs/<id>/brief.md`), is used by the reducer and by `task approve`. Accepting an update that does not move the brief no longer needs §A to match: the event records the first approval's hash, which stays in force, a warning says §A changed, and `check` still reports `frozen-text-changed`. Tests: `TestTaskUpdatedPlaceholderBriefIsNotAMove`, CLI `TestTaskUpdateApproveWithDriftedBrief`.
4. Time order (#23): documented below and covered by `TestTaskUpdatedTimeOrder`.
5. Event-level validation (#23). `TaskUpdated.Check` (called by `Event.Validate` and the reducer) applies git branch rules (now also `HEAD`, `@`, empty, dot-leading and `.lock` components, control characters) and relative in-repo path rules for `worktree` and `brief`, and no whitespace in `repo`. A merged-in bad event is listed as invalid by `check` and ignored. Tests: `internal/event/task_updated_test.go`, CLI `TestTaskUpdateMergedInvalidEvent`.
6. `contract show` with a missing or unreadable file (#24) exits 3 (`not_found`, `field: path`); documented. Test: `TestContractShowMissingFile`.

Contract text changes against my first handoff:

C-event-log v5 §5 row, replacing the earlier one:

| `update-after-close` | A `TaskUpdated` that comes after the task's `TaskDeferred` in log order. The CLI refuses it; it arrives through a git merge. (Done is observed, not logged, so a pending update on a done task is not a conflict; it can no longer be approved.) |

C-event-log v5 §6 `TaskUpdated` row, replacing the earlier one:

| `TaskUpdated` | Any subset of `repo, base_branch, branch, worktree, brief, title`, plus `reason`. At least one field besides `reason`. A present field is never empty; `branch` and `base_branch` are git branch names; `worktree` is a relative path inside the repository; `brief` is a relative path inside `.ekumen/`. An event that breaks these is invalid. Absent fields are unchanged. `TaskUpdated` and `TaskApproved` apply in log order (§2): an update that comes before the task's first `TaskApproved`, including one whose clock puts it before an approval it was written after, takes effect at once; one after it is pending until a later `TaskApproved`, which accepts every pending update before it (several merge field by field, newest wins). A pending update does not change derived status. On acceptance the task's `tier_grants` are the new approval's. Its §A hash is the new approval's only when the update moves the brief to another file (compared after dropping a leading `.ekumen/`; an empty brief is `briefs/<task>/brief.md`), otherwise the first approval's hash stands. A `TaskApproved` with nothing pending changes nothing (the first approval wins). |
