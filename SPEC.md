# Ekumen — a spine-driven workflow for running many AI coding sessions on one project

*Starter spec, v0.1. Name: Ekumen. Where this spec and VISION.md differ, VISION.md wins (e.g. the core is a Go CLI, not Python scripts). Everything here is generic; the running example is an invented project.*

---

## 1. The problem

One engineer runs a large project with AI coding agents: one **orchestrator** session holds the design, many **task** sessions build pieces in parallel, each in its own git worktree. This scales well, but four things break:

1. **Visibility.** Many sessions; any of them may be stuck waiting on the human. Finding what is blocked means scanning windows.
2. **Context collisions.** A decision often needs background. Asking for it in the session that raised it derails that session's main thread.
3. **Idle waiting.** Once a decision is made, dependent work could start on its own, but waits for the human to notice and start it.
4. **Drift.** Status lives in prose across several documents. They disagree, and agents reason confidently over stale state.

Ekumen keeps the discipline (frozen contracts, scoped briefs, single writers) and moves the bookkeeping into files that scripts can read and generate.

## 2. Running example (invented)

**Project:** split the billing module of a monolith into three services: `invoice-svc`, `payments-svc`, `ledger-svc`.

- Contracts: `C1` the `InvoiceIssued` event schema, `C2` the ledger table DDL, `C3` the payments API.
- Tasks: `T1` shared event library, `T2` invoice-svc producer, `T3` ledger-svc consumer, `T4` payments API, `T5` backfill job, `T6` cutover runbook.
- A decision that comes up: *"Ledger writes: synchronous call or transactional outbox?"*

## 3. Primitives

| Primitive | Purpose | Who writes | Lifecycle | Classic analogue |
|---|---|---|---|---|
| **Spine** | Design and rationale: what the system does, business rules, binding rules, precedence | Orchestrator, with the lead's approval | Living; history in git | RFC / program charter |
| **Contract** | An interface two or more tasks depend on | Orchestrator drafts, lead freezes | draft → frozen → changed only via protocol | Design-by-contract; final RFC |
| **Brief** | One task's world: scope, acceptance, out of scope, start prompt | §A orchestrator · §B orchestrator · §C task session | §A frozen on approval; §B, §C append-only | Work order + change orders + standup |
| **Decision** | A choice above a session's tier | Session raises, lead answers | pending → decided / defaulted / superseded | ADR |
| **Deviation** | Where the build differs from design | Generated from PR specs + decisions; risk sweep by hand | Append-only | Drift log |
| **Registry** | The task graph, machine-readable | Skills and scripts | Updated on every brief, decision, reconcile | Kanban board data |
| **State** | One snapshot of everything | `/reconcile` only | Regenerated | CQRS read model |
| **Map** | Human view of state | `/map` only | Regenerated | Kanban board |
| **Auditor** | Compares spine and contracts to authoritative state | Read-only agent | On demand / scheduled | Controller reconcile loop |

## 4. Invariants

1. **Single writer per section.** Ownership is the concurrency control; no two agents edit the same text.
2. **Freeze on approval.** No task session starts until its brief is approved. After approval, §A never changes; §B amends it.
3. **Append-only change.** §B, §C and decisions are never rewritten. History is the audit trail.
4. **Escalate, don't work around.** A session that thinks a contract is wrong stops and raises a decision. It never redefines the contract locally.
5. **Detect / act separation.** The auditor reports; it never edits. That makes it safe to run often.
6. **Authoritative inputs only.** Truth is the default branch on the remote, PR merged state and deployed versions. Never the working tree, never a ticket's status.
7. **One precedence rule,** written once in the spine: `merged code > contracts > spine > older design docs`.
8. **Generated, not maintained.** Anything that summarizes other files (status, map, deviation list) is produced by a script.
9. **External dependencies are gates.** Anything owned by another team on the critical path is a decision record with an owner, an asked-on date and a needed-by date, and it blocks the milestone that depends on it.

Commit `.ekumen/` to git. Git is the change log; the spine does not keep one.

## 6. Schemas

### 6.1 registry.yaml

```yaml
project: billing-split
lead: <github-handle>
tasks:
  T1:
    title: Shared event library
    brief: briefs/T1-event-lib.md
    approved: 2025-01-06        # null until approved
    blocked_by: []
    repo: billing
    base_branch: main
    branch: feat/t1-event-lib
    worktree: .worktrees/t1-event-lib
    session: null               # background session name once started
    status: done                # derived by /reconcile; do not hand-edit
    tier_grants: [push_own_branch, open_draft_pr, reply_review, restack, dev_apply_after_dry_run]
  T3:
    title: Ledger consumer
    brief: briefs/T3-ledger-consumer.md
    approved: 2025-01-07
    blocked_by: [T1, D-007]
    repo: billing
    base_branch: feat/t1-event-lib
    branch: feat/t3-ledger-consumer
    worktree: .worktrees/t3-ledger-consumer
    session: null
    status: blocked
    tier_grants: [push_own_branch, open_draft_pr, reply_review, restack]
external:
  X1:
    what: Payments provider sandbox credentials
    owner_team: platform
    asked_on: 2025-01-05
    needed_by: 2025-01-15
    blocks: [T4]
    status: waiting
```

`status` values: `draft`, `approved`, `blocked`, `ready`, `running`, `in_review`, `done`, `deferred`.

### 6.2 Decision record — decisions/D-007.yaml

```yaml
id: D-007
title: Ledger writes — synchronous call or transactional outbox?
tier: 2                     # 0 pre-authorized · 1 session decides, veto window · 2 lead must decide
raised_by: {task: T3, session: t3-ledger, on: 2025-01-09}
question: >
  invoice-svc must record a ledger entry for every issued invoice.
  Do we call ledger-svc synchronously or write to an outbox table and relay?
options:
  - id: sync
    tradeoff: Simple; invoice issuance fails when ledger-svc is down.
  - id: outbox
    tradeoff: Survives ledger outages; needs a relay worker and idempotent consumer.
recommendation: outbox
default_if_no_answer: null  # only allowed for tier 1
deadline: 2025-01-11
blocks: [T3, T5]
contract_impact: [C1]       # non-empty => approving it is a contract change
context:
  summary: >
    ≤150 words written by the raising session: why it came up, what was tried,
    what evidence exists. Enough to decide without opening the raising session.
  evidence:
    - briefs/T3-ledger-consumer.md#c-2025-01-09
    - contracts/C1-invoice-issued-event.md
    - https://github.com/<org>/billing/pull/123
  prior_decisions: [D-003]
status: pending             # pending | decided | defaulted | superseded
answer: null
answer_note: null
decided_by: null
decided_on: null
```

### 6.3 Decision tiers

| Tier | Who decides | Examples | Mechanism |
|---|---|---|---|
| **0 — pre-authorized** | The session, no record needed | Push own branch, open draft PR, reply to review threads on own PR, rebase/restack, dev apply already shown as a dry run | Listed in `tier_grants` on approval |
| **1 — in-contract choice** | The session, with a veto window | Naming, internal structure, test approach, a choice inside a frozen contract | Decision record with `default_if_no_answer`; applied by `/reconcile` after `deadline` |
| **2 — lead** | The lead only | Contract change, anything in production, outward actions to other teams, irreversible steps, release tags | Decision record, no default; blocks until answered |

Most of the waiting in this kind of project is tier 0 asked as if it were tier 2. Writing tier grants into each brief removes most of it.

### 6.4 Brief template — templates/brief.md

```markdown
---
id: T3
title: Ledger consumer
contracts_consumed: [C1, C2]
contracts_produced: []
blocked_by: [T1, D-007]
tier_grants: [push_own_branch, open_draft_pr, reply_review, restack]
---

# T3 · Ledger consumer

## §A Brief (frozen on approval)
**Goal:** …
**Context (verified on <date> against origin/main):** …
**Job:** numbered steps
**Touches:** packages / files
**Definition of done:** checklist (tests, PR spec, CI green, off by default, handoff written)
**Out of scope:** …
**Escalate if:** …
**Start prompt:**
    Read .ekumen/spine.md, then this brief, then contracts C1 and C2.
    Work only inside §A as amended by §B. Never edit the spine, contracts, §A or §B.
    Report only by appending to §C via /handoff. Raise anything above your tier with /blocked.

## §B Amendments (orchestrator; append-only, dated)
- <date>: approved by lead.

## §C Handoff (task session; append-only, dated)
```

Status is never written in the brief. It lives in the registry and is derived.

### 6.5 Contract header — templates/contract.md

```markdown
---
id: C2
title: Ledger table DDL
status: frozen          # draft | frozen
frozen_on: 2025-01-07
version: 1
consumers: [T3, T5]
producers: [T1]
---
```

Changing a frozen contract: a tier-2 decision with `contract_impact`, then a version bump, then a §B amendment to every consumer brief, then follow-up briefs for anything already merged.

### 6.6 state.json (generated)

```json
{
  "generated_at": "2025-01-09T10:00:00Z",
  "tasks": {"T3": {"status": "blocked", "blocked_by_open": ["D-007"], "prs": [], "session_state": null}},
  "decisions_open": [{"id": "D-007", "tier": 2, "deadline": "2025-01-11", "blocks": ["T3","T5"], "priority": 4.0}],
  "external_open": [{"id": "X1", "needed_by": "2025-01-15", "days_waiting": 4}],
  "prs": [{"repo": "billing", "number": 123, "task": "T1", "state": "merged"}],
  "drift": []
}
```

Decision priority = number of tasks blocked (transitively) × urgency of the deadline.

## 7. Skills

Each skill is a `SKILL.md` (instructions) plus scripts. Rule of thumb:

- **Judgment** (summarize, recommend, draft) → the instructions.
- **Anything that must be exact** (parse YAML, update registry, render HTML, validate) → a script the skill calls.
- **Anything that must never be skipped** → a hook, not a skill.

| Skill | Run in | Reads | Writes | Script part | Model part |
|---|---|---|---|---|---|
| `/ekumen-init` | New project, once | Optional design doc | `.ekumen/` skeleton, spine draft, empty registry | Create folders, copy templates | Draft the spine from the design doc |
| `/brief <id>` | Orchestrator | Spine, contracts, registry | Brief §A, registry row | Add registry row and front matter | Scope, acceptance, out of scope, start prompt |
| `/approve <id>` | Orchestrator, on lead's word | Brief | §B "approved" line, `approved` date, tier grants | All of it | — |
| `/blocked` | Task session | Own brief and context | `decisions/D-n.yaml`; registry `blocked_by` | Next id, schema check, registry update | Question, options, recommendation, context packet ≤150 words with evidence links |
| `/decide <id>` | **Fresh side session** | That one decision and its evidence | Answer; §B amendment to every brief in `blocks`; registry unblocked; message to running sessions | Write answer, append §B, unblock, notify | Answer the lead's follow-up questions using tools |
| `/handoff` | Task session | Brief, git, PRs | Dated §C entry (STATUS / PRs / DECISIONS / FOLLOW-UPS / DEVIATIONS); optional tracker comment | Required-field check, tracker post | Short, honest summary |
| `/reconcile` | Orchestrator, daily or on demand | New §C entries, decisions, registry, PR state, session state | `state.json`; tier-1 defaults applied past deadline; proposed spine edits; new decisions for follow-ups | Gather state, apply defaults, write `state.json` | Decide which findings change the design; draft spine edits for approval |
| `/audit` | Read-only session or scheduled | Spine and contracts vs remote default branch, PRs, deployed versions | Report only | `git fetch`, collect SHAs and versions | Spot drift: contract violations, stalled work, external dependencies with no owner or date |
| `/map` | Anyone; after `/reconcile` | `state.json` | `map.html` | All of it (template render) | — |

### Map layout

Top to bottom:
1. **Waiting on you** — open tier-2 decisions by priority, each showing what it blocks and a one-line context summary. Then tier-1 decisions with an open veto window.
2. **External dependencies** — owner, asked on, needed by, days waiting.
3. **Running / ready / blocked** task counts and the task graph.
4. **PRs** by state.
5. **Drift** from the last audit.

## 8. Dispatcher (a script, not a skill)

Runs every few minutes (a loop or a launchd/cron job).

```
for task in registry.tasks:
    if task.status in (ready,) and task.approved and all blockers done/decided and task.session is null:
        git worktree add <worktree> -b <branch> origin/<base_branch>
        start background session named <task id> with the brief's start prompt
        registry: session = <name>, status = running
for decision decided since last run:
    for task in decision.blocks with a live session:
        send the session: "D-n decided: <answer>. Your brief §B has the amendment."
```

It only ever starts tasks the lead already approved. Cross-session messages are information, never approval.

## 9. Hooks (guardrails as code)

| Rule | Hook |
|---|---|
| Task sessions never edit spine, contracts, §A or §B | Before Edit/Write: deny unless the session is the orchestrator (key on session name or working directory) |
| §C and decisions are append-only | Before Edit/Write on a brief: reject if the diff removes or changes existing §C lines |
| Reason over authoritative state | At session start: `git fetch`; warn if the checkout is behind or not on the expected branch |
| PR spec present and complete | Before `gh pr create`: run `validate_pr_spec.py` |
| No internal ids in public PR text; no local `replace`/path overrides before merge | Same validator, plus a pre-push check |
| Never touch production / never cut release tags | Permission deny rules |
| Lead is pinged when needed | Notification hook on "needs input" / permission prompt → desktop or push notification |

## 10. PR spec (per PR)

One markdown file per PR in the repo it changes, e.g. `docs/pr-specs/<slug>.md`:

1. What and why
2. Where it sits in the flow (small diagram)
3. Contracts consumed or produced, with versions
4. Low-level design (files, types, SQL/DDL verbatim, control flow, errors and retries, concurrency, config, metrics, logs)
5. Edge cases and failure modes
6. Tests and how to run them
7. Rollout and rollback
8. Out of scope / follow-ups
9. Deviations from brief or contract (feeds `deviations.md`)

Keep merge order and stack position out of the spec; they go stale on every restack. Use a lighter variant for config-only PRs.

## 11. One decision, end to end

1. The T3 session needs to know sync vs outbox. That is tier 2. It runs `/blocked`, which writes `D-007.yaml` and marks T3 and T5 blocked. It keeps working on its test fixtures.
2. A notification fires. The map shows D-007 at the top of *Waiting on you*: blocks 2 tasks, deadline in 2 days, recommendation outbox.
3. The lead opens a new session: `/decide D-007`. It asks "how big is the relay worker?" and gets an answer there. The T3 session never sees this conversation.
4. The lead answers `outbox`. The script appends §B to T3 and T5, clears `D-007` from their `blocked_by`, and messages the live T3 session.
5. The dispatcher sees T5 is ready and starts it. `/reconcile` then `/map` refresh the page.

One decision, one place, its context beside it.

## 12. Lessons that shaped this

- **Agents are only as good as the freshness of their inputs.** Most confident wrong conclusions came from reading a working tree parked on another branch, or from trusting a ticket's status.
- **A source of truth drifts unless something closes the loop.** Detecting drift without folding it back just makes a longer to-do list.
- **Hand-written status lies.** Headers that say "draft" long after approval are the normal outcome, not a lapse.
- **Most human blocking is permission, not judgment.** In practice the large majority of "waiting on the lead" items were push/PR/reply/apply permissions.
- **Internal throughput can hide the real blocker.** A project can ship every internal piece on time while a dependency owned by another team sits in a table with no owner or date. External dependencies need dates and gates.
- **Logs crowd out design.** When most of the text is status and history, readers stop finding the design. Put history in git.
- **Precedence rules multiply.** Pick one, write it once.

## 13. Build order

1. **v0.1 — decisions + map.** `templates/decision.yaml`, `ekumen CLI` (new decision, answer decision, list open), `/blocked`, `/decide`, `render_map.py`, `/map`. Fixes visibility and context collisions.
2. **v0.2 — registry + reconcile.** `registry.yaml`, derived status, `/reconcile` with tier-1 defaults, external dependencies on the map.
3. **v0.3 — dispatcher.** Auto-start ready tasks; message running sessions on decisions.
4. **v0.4 — hooks.** Spine protection, append-only §C, fetch-on-start, PR spec validator, notifications.
5. **v0.5 — audit.** Generic read-only drift auditor.
6. **Later.** Packaging as a plugin; the map as a hosted page where decisions can be answered directly; adapters for issue trackers.

## 14. Open questions

- Should decisions live in files (git-native, reviewable) or a small database (live map, answer from the page)? Files first; a sync layer later.
- How should a session prove its tier-1 choice stayed inside the contract? Possibly a contract-check script per contract.
- How does this work with more than one human approver? Per-area owners with their own decision rights in the registry.
- Measuring value: time from decision raised to answered, time tasks spend blocked, hours spent reconciling, defects caught by contracts or audits.

## 15. Platform features to verify before building

The design assumes the agent tool provides: background sessions with a state listing (including "needs input"), named sessions you can message, forking a side session, pre/post tool-use and session-start hooks, notification hooks, skills with bundled scripts, and scheduled or looped runs. Check the current docs for exact command names, flags and frontmatter fields before relying on them.
